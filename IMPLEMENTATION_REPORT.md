# Отчёт по доработке PlannerApp

Дата проверки: 25 июля 2026.

## Реализовано

- Полные правила повторения: ежедневно, по будням, еженедельно, раз в две недели, ежемесячно и ежегодно. Серии имеют UUID, исходную дату и номер экземпляра; повторное завершение старой задачи не создаёт новую ветку серии.
- При завершении текущий экземпляр остаётся в истории, а следующий создаётся в статусе «Запланировано». Пропущенные даты не материализуются; копируются проект, теги, приоритет, заметки, флаг канбана и только незавершённые пункты чеклиста.
- Редакторы задач и проектов на macOS/iOS работают через локальные черновики. Сохранение модели и идемпотентной outbox-мутации выполняется одним `ModelContext.save()`, отмена не изменяет SwiftData.
- В задачу добавлен отдельный флаг «Показывать в канбане». Старое исключение по строке «Дни рождения» преобразуется в этот флаг один раз при data repair.
- Канбан получил точную позицию вставки, индикатор, нормализацию порядка, быстрый ввод, фильтры по проекту/приоритету и доступные команды перемещения без drag-and-drop.
- iOS-календарь получил режимы «Неделя/День», all-day область, 24-часовую сетку, переход по дням, начальную прокрутку и изменение длительности с шагом 30 минут. macOS раскладывает пересечения по дорожкам. Диапазоны через полночь разбиваются по дням, а перенос сохраняет исходное время и длительность.
- Введены `PlannerSchemaV1`, `PlannerSchemaV2` и `PlannerMigrationPlan`. Перед открытием store создаётся копия store/WAL/SHM с SHA256 manifest; сохраняются три последние копии. После открытия проверяются ID, связи, настройки и серии. Ошибка показывает экран восстановления с повтором, диагностикой и откатом.
- JSON backup обновлён до v2; импорт v1 сохраняется с безопасными значениями по умолчанию.
- Синхронизация переведена на v2: persistent outbox, UUID мутаций, `baseRevision`, серверные revisions, постраничный change log, подтверждённые удаления, конфликты с выбором server/local/copy, HTTPS + pinning, RFC3339 с долями секунды, один sync-сеанс и backoff.
- Backend использует нумерованные транзакционные SQL-миграции, pre-migration backup, защиту от более новой схемы и таблицы `entity_heads`, `change_log`, `applied_mutations`. API v1 недоступен.
- Добавлен средний iOS-виджет «Задачи на сегодня». Он сам загружает минимальный read-only snapshot по HTTPS, проверяет SHA256 fingerprint сертификата, хранит резервный кэш внутри extension и обновляет дни с учётом DST. App Groups не используются, поэтому виджет подписывается бесплатным Personal Team; в конфигурацию вводится отдельный read-only токен, не основной sync token.
- Backend получил `GET /v2/widget/snapshot` и отдельный `PLANNER_WIDGET_TOKEN`. Этот токен не принимается sync-endpoints, а snapshot не содержит заметок, чеклистов, тегов и других приватных полей.

## Переход сервера на v2

1. Остановить старые клиенты и backend v1.
2. Архивировать старую SQLite БД вместе с `-wal`/`-shm`, затем убрать её из активного volume.
3. Развернуть backend v2 и проверить, что `/v2/sync/status` сообщает `protocolVersion: 2` и `isEmpty: true`.
4. На основном устройстве выполнить «Инициализировать пустой сервер».
5. Остальные устройства переподключить к v2 и принять состояние сервера вместо старого локального sync-state.

`/v2/sync/initialize` возвращает конфликт, если сервер уже содержит данные. Повторная destructive-инициализация через API отсутствует.

## Развёртывание 25 июля 2026

- Backend обновлён в `/opt/planner-sync` с резервной копией прежних исходников.
- Существующие SQLite volume, основной sync token и TLS-сертификат сохранены.
- Новый widget endpoint доступен снаружи по HTTPS и возвращает HTTP 200.
- Разделение прав проверено: widget token получает HTTP 401 на мутациях, основной sync token — HTTP 401 на widget endpoint.
- TLS fingerprint остался прежним, контейнер `planner-sync` работает, VPN-интерфейс `awg0` сохранил состояние `UP`.
- Временный SSH-ключ и передаваемые секреты удалены с Mac и VPS; повторная авторизация временным ключом отклонена.

## Оставшаяся эксплуатационная проверка

Автоматические тесты не заменяют smoke-проверку на подписанных приложениях и реальном сервере. Перед production rollout нужно вручную пройти редакторы, drag/resize календаря и канбана на целевых версиях macOS/iOS, а также выполнить двухустройственный сетевой сценарий с реальным HTTPS-сертификатом и обрывом соединения.
