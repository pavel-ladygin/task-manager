# Архитектурный отчёт: создание задач в Planner через Telegram

Дата: 7 сентября 2026 года  
Проект: Apple-native Planner (`SwiftUI + SwiftData + Go sync backend + SQLite`)

## 1. Резюме

Цель: пользователь отправляет боту текст или голосовое сообщение, например «сходить посрать в 18:00», а бот создаёт задачу в Planner и отвечает подтверждением.

Рекомендуемое решение — **добавить Telegram-модуль в существующий Go backend**, но не давать боту прямой доступ к SQLite и не заставлять его подделывать клиент синхронизации. В backend следует выделить единый серверный сценарий `CreateTask`, который валидирует данные и атомарно добавляет задачу в текущий журнал изменений v2. Telegram — только ещё один вход в этот сценарий.

Для первой версии достаточно:

1. Telegram webhook для текста и голоса.
2. Облачное распознавание речи, чтобы не перегружать текущий VPS.
3. Комбинированный разбор команды: обычные правила для дат и времени, модель — только как резерв для сложных фраз.
4. Ответ бота с тем, как именно была понята задача.
5. Синхронизация открытого приложения каждые 10–15 секунд либо SSE-сигнал «появились изменения».

Отдельно важно: сейчас Planner синхронизируется при запуске, смене состояния окна, локальном редактировании и вручную. Если задача пришла снаружи, уже открытое и бездействующее приложение может не узнать о ней. Поэтому «создать на сервере сразу» и «сразу показать в приложении» — две разные части задачи.

## 2. Что уже есть в проекте

- Нативные клиенты macOS/iOS хранят данные локально в SwiftData.
- Go backend хранит актуальные сущности и монотонный журнал изменений в SQLite.
- Протокол синхронизации v2 уже поддерживает идемпотентные мутации и конфликты по `baseRevision`.
- У задачи уже есть необходимые поля: `title`, `status`, `priority`, `scheduled`, `due`, даты создания/изменения и связи.
- В приложении есть голосовой ввод через Apple Speech, но он распознаёт микрофон внутри приложения. Голосовой файл из Telegram поступает на сервер, поэтому этот код повторно использовать нельзя.
- Backend сейчас ограничен 0,5 CPU и 256 МБ RAM. Полноценное локальное распознавание речи в том же контейнере будет медленным или потребует увеличения ресурсов.

## 3. Общий функциональный конвейер

Независимо от выбранной архитектуры бизнес-процесс должен выглядеть одинаково:

```text
Telegram text/voice
        │
        ▼
проверка user_id/chat_id + защита webhook
        │
        ▼
текст напрямую / загрузка voice → speech-to-text
        │
        ▼
разбор: title, scheduled, due, priority, project
        │
        ▼
валидация + идемпотентное создание задачи
        │
        ├──► ответ в Telegram
        │
        └──► change log v2 ──► синхронизация Planner
```

Пример результата разбора:

```json
{
  "title": "Сходить посрать",
  "scheduled": "сегодня в 18:00 по Europe/Moscow",
  "status": "planned",
  "priority": "none"
}
```

Бот должен ответить не просто «Готово», а, например:

> ✅ Создал: «Сходить посрать» — сегодня, 18:00

Если фраза неоднозначна или указанное время сегодня уже прошло, безопаснее показать кнопки «Сегодня», «Завтра», «Без времени» и создавать окончательную задачу после выбора. Для однозначных фраз задача создаётся сразу.

## 4. Вариант A — Telegram внутри существующего Go backend

### Схема

```text
Telegram ──webhook──► planner-sync
                         ├─ Telegram handler
                         ├─ voice transcription client
                         ├─ natural-language parser
                         └─ CreateTask service ─► SQLite/change log
```

### Реализация

- Добавить endpoint `POST /telegram/webhook/<непредсказуемый-путь>`.
- Дополнительно проверять заголовок `X-Telegram-Bot-Api-Secret-Token`.
- Разрешить команды только от заранее заданного Telegram `user_id`; не полагаться на username.
- Для voice получить `file_id`, вызвать `getFile`, скачать OGG/Opus во временный файл и отправить его сервису распознавания.
- Выделить внутри backend сервис `CreateTask`, чтобы Telegram handler и будущие интеграции не писали напрямую в таблицы.
- Создавать новую задачу как серверное изменение с уникальным UUID и отдельным `sourceDeviceID`, например `telegram-bot`.
- Использовать `update_id` Telegram как ключ идемпотентности, чтобы повторная доставка webhook не создавала дубликаты.
- Отправлять подтверждение только после успешной фиксации транзакции.

### Плюсы

- Минимум новых компонентов и самый короткий путь к рабочей версии.
- Используется текущая SQLite-база и журнал ревизий.
- Простые развёртывание, резервное копирование и диагностика.
- Нет дополнительного внутреннего API и отдельной сети между сервисами.

### Минусы

- Telegram, распознавание и основной sync backend оказываются в одном процессе.
- Ошибки интеграции могут влиять на синхронизацию, если не поставить таймауты и ограничения.
- При росте функциональности модуль придётся отделять.

### Когда выбирать

Для личного однопользовательского Planner и текущего VPS — **лучший вариант**.

## 5. Вариант B — отдельный `planner-bot` сервис

### Схема

```text
Telegram ──webhook──► planner-bot ──restricted ingest API──► planner-sync
                          │                                      │
                          └─ STT + parser                        └─ SQLite/change log
```

### Реализация

- Поднять второй Go-контейнер `planner-bot`.
- Добавить в основной backend узкий endpoint `POST /v1/ingest/tasks`.
- Защитить endpoint отдельным write-only токеном, который умеет только создавать задачи и не даёт читать журнал, менять настройки или удалять сущности.
- Передавать `Idempotency-Key: telegram:<update_id>`.
- Валидацию доменных полей и запись в журнал оставить в `planner-sync`.
- Если обработка голоса станет долгой, добавить маленькую долговечную очередь заданий. Для одного пользователя достаточно SQLite-очереди; Redis/NATS пока избыточны.

### Плюсы

- Сбой распознавания или Telegram API не затрагивает основной sync-процесс.
- Независимые обновления и лимиты ресурсов.
- Удобнее добавлять команды `/today`, редактирование и несколько каналов ввода.
- Секрет основного sync API не попадает в bot-сервис.

### Минусы

- Больше кода, контейнеров, логов и проверок доступности.
- Требуется внутренний API и его версионирование.
- Для текущей нагрузки преимущества изоляции могут не окупить сложность.

### Когда выбирать

Если бот станет отдельным продуктовым модулем, появятся несколько пользователей или тяжёлая обработка голоса.

## 6. Вариант C — n8n как слой автоматизации

### Схема

```text
Telegram Trigger ─► text/voice branch ─► STT ─► parser
                                             │
                                             ▼
                               POST /v1/ingest/tasks ─► Planner
```

### Реализация

- Развернуть n8n на том же VPS или использовать облачный n8n.
- Собрать workflow: Telegram Trigger → проверка `user_id` → загрузка файла → speech-to-text → разбор JSON → HTTP Request → Telegram confirmation.
- Основной backend всё равно должен получить узкий ingest endpoint; прямой доступ n8n к SQLite запрещён.
- Для self-hosted варианта обеспечить отдельный публичный HTTPS адрес и резервное копирование конфигурации n8n.

### Плюсы

- Самый быстрый способ проверить UX и формулировки команд.
- Workflow видно визуально; легко заменить провайдера распознавания.
- Удобно добавлять ветки, уведомления и ручное подтверждение.

### Минусы

- Дополнительный тяжёлый сервис для одного небольшого сценария.
- Логика хуже тестируется и ревьюится, чем Go-код в репозитории.
- Секреты и персональные расшифровки оказываются ещё в одной системе.
- Обработка повторов и транзакционная идемпотентность всё равно должны жить в Planner backend.

### Когда выбирать

Если приоритет — проверить идею за вечер и часто менять workflow без пересборки backend. Для постоянной эксплуатации затем можно перенести отлаженную логику в Go.

## 7. Вариант D — локальный процесс на Mac с long polling

### Схема

```text
Telegram ◄──getUpdates── Mac helper ─► локальное приложение/локальный API
```

### Реализация

- Небольшой фоновый helper на Mac забирает обновления методом `getUpdates`.
- Helper передаёт структурированную команду запущенному Planner через XPC/локальный endpoint.
- Не следует одновременно открывать один SwiftData store из независимых процессов без специально спроектированной координации.

### Плюсы

- Не нужен публичный webhook.
- Можно быстро сделать текстовый прототип.
- Персональные данные можно обрабатывать локально, если распознавание тоже локальное.

### Минусы

- Mac должен быть постоянно включён и подключён к интернету.
- Для iPhone и удалённого сценария это ненадёжно.
- Автозапуск, обновления и межпроцессное взаимодействие добавляют macOS-специфичную сложность.
- Telegram запрещает одновременно использовать `getUpdates` и webhook для одного бота.

### Когда выбирать

Только как локальный эксперимент либо когда принципиально нельзя принимать входящие соединения на VPS.

## 8. Сравнение вариантов

Оценки: 1 — плохо/сложно, 5 — хорошо/просто.

| Скорость запуска | 4 | 3 | 5 | 3 |
| Простота эксплуатации | 5 | 3 | 3 | 2 |

Итог:

## 9. Как обеспечить появление задачи «сразу»

В текущем приложении внешнее серверное изменение не инициирует синхронизацию само. Возможны три уровня:

### Уровень 1: простая периодическая синхронизация

- Пока приложение активно, запрашивать изменения раз в 10–15 секунд.
- При возвращении приложения на экран синхронизировать немедленно — это уже реализовано.
- Задача появится с задержкой до интервала опроса.

Это лучший MVP: работает без Apple Push и почти не усложняет backend.

### Уровень 2: SSE/WebSocket для открытого приложения

- Открытый Planner держит лёгкое соединение с backend.
- Backend отправляет только номер новой ревизии, без всей задачи.
- Клиент вызывает существующий безопасный pull v2.
- При разрыве соединения остаётся fallback на периодический опрос.

Это даёт почти мгновенное появление на открытом Mac и сохраняет текущую модель синхронизации.

### Уровень 3: APNs для закрытого/фонового iOS-приложения

- Backend посылает фоновое push-событие, клиент просыпается и делает pull.
- Доставка фоновых уведомлений системой не гарантируется и может ограничиваться.
- Требуется настроить Apple capability, регистрацию device token и серверные APNs credentials.

APNs полезен позже, но не должен быть единственным механизмом корректности. Источником истины остаётся журнал изменений; при каждом запуске выполняется обычный pull.

## 10. Разбор естественного языка

Рекомендуется гибридная схема:

1. Нормализовать распознанный текст.
2. Правилами извлечь явные конструкции: `в 18:00`, `завтра`, `в пятницу`, `через 2 часа`, `до 20:00`.
3. Остаток строки превратить в заголовок.
4. Для сложных фраз вызвать модель со строгой JSON-схемой.
5. Проверить результат доменными правилами и временной зоной `Europe/Moscow`.

Причина: простые команды должны быть быстрыми и предсказуемыми, а модель нужна для конструкций вроде «в следующий четверг после обеда напомни подготовить отчёт, срочно».

Политики, которые надо зафиксировать до реализации:

- `в 18:00` — сегодня, если время ещё не прошло; иначе спросить или предложить завтра;
- `до 18:00` заполняет `due`, а `в 18:00` — `scheduled`;
- команда без даты создаётся в `inbox`;
- команда с датой/временем создаётся в `planned`;
- исходную расшифровку можно временно хранить в `notes`, но аудиофайл после обработки удалять;
- при низкой уверенности распознавания не создавать молча неверную задачу.

## 11. Контракт рекомендуемого ingest API

Даже для варианта A полезно сформулировать внутреннюю команду отдельно от Telegram DTO:

```http
POST /internal/v1/tasks
Authorization: Bearer <отдельный ingest token>
Idempotency-Key: telegram:<update_id>
Content-Type: application/json
```

```json
{
  "source": "telegram",
  "title": "Сходить посрать",
  "scheduled": "2026-09-07T18:00:00+03:00",
  "due": null,
  "status": "planned",
  "priority": "none",
  "notes": ""
}
```

Ответ:

```json
{
  "taskID": "uuid",
  "revision": 123,
  "created": true
}
```

При повторе того же `Idempotency-Key` сервер должен вернуть тот же `taskID`, а не создавать новую задачу.

## 12. Безопасность и надёжность

Обязательный минимум:

- allowlist числового Telegram `user_id`;
- webhook secret header и непредсказуемый URL;
- отдельные секреты Telegram, ingest и Planner sync;
- никаких токенов в логах;
- лимит размера и длительности voice;
- таймауты на скачивание и speech-to-text;
- временные аудиофайлы с гарантированным удалением;
- дедупликация по `update_id`;
- журнал обработки: `received → transcribed → parsed → committed → replied`;
- повтор ответа Telegram не должен повторно создавать задачу;
- резервное копирование SQLite вместе с данными идемпотентности.

Telegram повторяет webhook при неуспешном HTTP-ответе, поэтому handler должен быстро подтвердить приём, а потенциально долгую обработку голоса выполнять как фоновую работу. Для текста допустима синхронная обработка, если она гарантированно укладывается в короткий таймаут.

## 13. Рекомендуемый план внедрения

### Этап 1 — текстовый MVP

- Telegram webhook в Go backend.
- Только личный `user_id`.
- Команды с простыми датами/временем.
- Идемпотентное создание задачи в change log.
- Ответ с интерпретированными полями.
- Foreground polling в Planner каждые 10–15 секунд.

Оценка: 2–4 инженерных дня вместе с тестами и развёртыванием.

### Этап 2 — голос

- Загрузка voice через Bot API.
- Подключение speech-to-text.
- Ограничения, таймауты, очистка файлов.
- Кнопки исправления при неоднозначности.

Оценка: ещё 2–4 дня.

### Этап 3 — мгновенная доставка и расширенные команды

- SSE для активного macOS-клиента.
- APNs как дополнительный канал для iOS, если подходит текущая схема подписи.
- `/undo`, `/today`, выбор проекта, приоритет, повторяющиеся задачи.

Оценка: ещё 3–7 дней в зависимости от APNs и UX подтверждений.

## 14. Финальное решение

Для этого проекта стоит выбрать **вариант A** и построить его так, чтобы позже без изменения доменной логики перейти к варианту B:

```text
сейчас: Telegram handler ─► CreateTask ─► Store
позже:  planner-bot ─► ingest API ─► CreateTask ─► Store
```

Ключевое архитектурное решение — не «как принять сообщение Telegram», а **создать единый серверный вход для добавления задач**, который обеспечивает валидацию, идемпотентность и запись в revision log. Тогда Telegram, Siri/Shortcuts, CLI и будущие интеграции смогут использовать один и тот же надёжный механизм.
